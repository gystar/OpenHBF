# OpenHBF 实验与测试执行规范

## 1. 目的与适用范围

本文是 OpenHBF 所有代码验证、功能实验、故障实验、性能测量和回归测试的统一执行规范。它规定如何设计、运行、记录和解释实验，避免不可重放结果、源码树污染、假测试通过和实现状态误报。

本文是实验执行的权威来源。各模块 HLD 负责描述“需要证明什么”，LLD 负责描述“fixture、输入、oracle和测试接缝是什么”，本文负责规定“实验必须怎样执行和留下证据”。若专项 HLD/LLD 与本文冲突，以更严格的约束为准，并在合入前修正文档冲突。

适用对象包括：

- unit、component、integration、system和conformance test；
- reset、fault、determinism、stress和sanitizer测试；
- latency、bandwidth、scaling和resource ceiling实验；
- 手工编译探针、调试复现和文档中的实现状态更新；
- 人工开发者、CI以及所有协作agent。

## 2. 强制阅读与文档接入

执行实验前必须依次阅读：

1. `docs/README.md`和`docs/任务更正方案.md`；
2. 本文；
3. 被测模块对应HLD/LLD；
4. `docs/HLD_08_VERIFICATION_CONFORMANCE.md`、`docs/LLD_08_VERIFICATION_CONFORMANCE.md`；
5. 涉及OCP行为时阅读PDF对应原文；涉及Ramulator ABI时阅读当前submodule源码。

仓库根`AGENTS.md`负责使agent自动发现本文。新增或修改HLD/LLD时，其“测试与验收”章节必须包含以下引用：

```markdown
实验执行、证据保存和状态更新统一遵循
[`实验与测试执行规范.md`](实验与测试执行规范.md)。
```

专项文档不得复制一份不同的通用实验流程，只补充本模块特有的fixture、oracle、参数和artifact。

## 3. 实验分级与证据含义

| 级别 | 名称 | 允许证明的内容 | 不允许声称 |
|---|---|---|---|
| E0 | Compile Probe | 单个头文件或translation unit可按指定标准编译 | target可链接、功能正确、正式构建通过 |
| E1 | Unit Test | 单一生产组件在明确fixture下满足局部oracle | 完整pipeline、跨模块行为或OCP conformance |
| E2 | Component Integration | 多个真实生产组件的公开接口契约 | 全系统driver等价或完整设备行为 |
| E3 | System Test | 真实`OpenHbxSystem`及指定生产pipeline的端到端行为 | 未覆盖能力或外部规范缺口已关闭 |
| E4 | Conformance/Performance | 对照规范vector或理论resource ceiling的正式证据 | vendor未提供参数是OCP保证值 |

Fake只能替代明确的外部sink、clock-independent input或受控fault source。使用fake生产模块的测试最多形成E1/E2证据，不能把真实Host、Controller、FTL或Media pipeline标成`VERIFIED`。

## 4. 实验定义模板

每个新增实验或测试必须在代码、manifest或对应LLD中记录以下字段：

| 字段 | 要求 |
|---|---|
| Experiment ID | 稳定唯一，例如`EXP-02-RESET-001`或已冻结`VER-*` ID |
| Requirement | 对应OCP、Ramulator、HLD/LLD或OpenHBF requirement ID |
| Objective | 一句话说明要证明或证伪什么 |
| Evidence level | E0至E4 |
| Production path | 实际经过的生产模块；列出被fake替代的边界 |
| Preconditions | revision、依赖、Docker image、capability和数据模式 |
| Config | canonical config hash及全部override |
| Workload | trace/generator版本、request数、地址范围和hash |
| Seed | 固定整数；无随机行为写`not-applicable` |
| Oracle | 可自动判定的精确条件，不使用“看起来合理” |
| Budget | 最大模拟cycle、request数及宿主timeout |
| Artifacts | 成功和失败必须保存的结果 |
| Replay | 可直接执行的重放命令 |

没有oracle、seed/config记录或重放入口的性能数字不得进入结论、图表或实现状态证据。

## 5. 目录与生成物规则

### 5.1 允许位置

- 正式CMake构建：日常构建统一位于`build/tests/`；需要隔离的Ramulator或sanitizer变体使用`build/tests-<profile>/`，不得在`build/tests/`下再增加`default`层。
- 临时单文件编译：`/tmp/openhbf-<purpose>/`或`mktemp -d`创建的目录。
- 实验artifact：统一位于`build/artifacts/<suite>/<experiment-id>/<run-id>/`，不得散落到各构建树。
- CI artifact：CI提供的外部artifact目录，但manifest必须记录其逻辑路径。

### 5.2 禁止位置

禁止在仓库根目录、`src/`、`include/`、`tests/`、`docs/`和`configs/`生成：

- `.o`、`.obj`、`.a`、`.so`、可执行文件；
- `a.out`、core dump、coverage原始文件；
- 实验CSV/JSON、日志、图片、临时配置和数据镜像。

手工编译必须显式指定输出：

```bash
probe_dir="$(mktemp -d)"
g++ -std=c++17 -Wall -Wextra -Wpedantic -Werror \
  -Iinclude -c src/integration/host_request.cpp \
  -o "${probe_dir}/host_request.o"
```

不得运行缺少`-o`的`g++ -c source.cpp`。实验结束后只删除本次明确创建的目录，不使用未解析变量、仓库根路径或宽泛递归删除命令。

## 6. 标准执行流程

### 6.1 实验前

1. 记录`git status --short`，识别用户已有改动，不得回退无关文件。
2. 确认Experiment ID、requirement、证据级别和oracle。
3. 校验canonical config、capability、payload mode和seed。
4. 检查被测target确实链接预期生产文件，避免漏链接后假通过。
5. 为build和artifact选择合规目录。

### 6.2 构建

正式证据使用Docker Compose：

```bash
docker compose up -d dev
docker compose exec -T dev cmake -S . -B build/tests \
  -DOPENHBF_BUILD_TESTS=ON -DCMAKE_BUILD_TYPE=Debug
docker compose exec -T dev cmake --build build/tests -j2
```

至少保持C++17、`-Wall -Wextra -Wpedantic -Werror`。Ramulator自身需要的语言标准必须限制在第三方或adapter target，不能静默提高OpenHBF core标准。

### 6.3 执行

优先通过CTest名称或label运行：

```bash
docker compose exec -T dev ctest --test-dir build/tests \
  -L openhbf_integration --output-on-failure
```

禁止用宿主wall-clock替代模拟cycle判据。宿主timeout只能作为hang guard；功能、时序和性能通过条件必须来自模拟状态、cycle、resource或terminal结果。

### 6.4 实验后

1. 保存resolved config、seed、workload hash、binary/revision和完整命令。
2. 检查accepted/issued/terminal/outstanding、bytes和event守恒。
3. 失败时保存首个分歧token、前后事件窗口和非idle owner snapshot。
4. 扫描源码树是否出现生成物。
5. 仅依据实际证据更新HLD/LLD和traceability状态。

生成物扫描基线：

```bash
find . -path './.git' -prune -o \
  -path './build-*' -prune -o \
  -type f \( -name '*.o' -o -name '*.a' -o -name '*.so' \
  -o -name 'a.out' \) -print
```

该命令输出非空时，实验尚未完成交付。

## 7. Oracle与守恒要求

所有Accepted操作必须满足：

```text
accepted = terminal + outstanding
```

并至少检查：

- Retry/Backpressured前后设备状态、token、payload ownership和event数量不变；
- callback精确一次，terminal前后生命周期有序；
- reset后的旧generation事件不提交新状态；
- issue时未来持久状态不可见，只在terminal completion提交；
- read payload、CECC data-valid、failure data-invalid符合typed status；
- Host、cache和Media bytes不重复计入有效吞吐；
- 相同config、seed、workload和binary的observable digest一致。

性能实验还必须给出理论上限公式、有效measurement window、warmup策略和误差解释。只报告平均值不足以证明正确性；至少报告样本数、分位数或min/max，以及是否触及queue、link、Bank或Media资源上限。

## 8. Artifact最小集合

每次E3/E4实验至少保存：

```text
manifest.json
resolved-config.yaml
command.txt
stdout.log
stderr.log
completion-summary.json
stats.json
event-digest.txt
final-snapshot.json
```

失败额外保存：

```text
failure.json
event-window.jsonl
outstanding.json
replay.sh
```

`manifest.json`必须包含Experiment ID、UTC时间、revision、dirty状态、compiler、build type、binary hash、Docker image、seed、workload hash、capability和证据级别。artifact不得包含依赖pointer地址或宿主调度顺序的oracle字段。

## 9. 状态更新规则

| 代码与证据 | 文档允许状态 |
|---|---|
| 只有设计或计划文件 | `PLANNED` |
| 部分代码或仅E0探针 | `PARTIAL`或`IMPLEMENTED`，不得写`VERIFIED` |
| 生产代码完成但测试未运行 | `IMPLEMENTED` |
| 对应E1/E2自动测试通过 | 仅该组件可写`VERIFIED`，系统仍保持较低状态 |
| 真实production pipeline的E3/E4通过 | 对应端到端requirement可写`VERIFIED` |
| 外部规范或vendor数据缺失 | 保持`EXTERNAL_DEPENDENCY`或`BLOCKED_SPEC` |

文档必须同时写明：运行日期、命令/CTest label、通过数量、构建选项和未覆盖范围。旧build目录、历史日志、手工`g++`成功或agent口头报告不能单独作为状态更新证据。

## 10. Review清单

实验或测试合入前逐项确认：

- [ ] Experiment ID和requirement可追溯。
- [ ] 使用正确证据级别，没有fake冒充生产pipeline。
- [ ] 输入、config、seed、workload和oracle冻结。
- [ ] Retry、failure、reset和边界情况有负向测试。
- [ ] 测试通过公开接口观察，不直接修改私有状态。
- [ ] 正式证据来自Docker、CMake和CTest。
- [ ] artifact足以独立重放失败。
- [ ] 状态更新没有超过证据覆盖范围。
- [ ] 源码树不存在生成物或实验输出。
- [ ] HLD/LLD、traceability和测试名保持一致。

任何一项未满足时，实验可以作为开发诊断，但不能作为正式验收证据。
