## 1. 目的与基本原则

### 1.1 目的

OpenHBX设计文档直接服务于架构评审、代码实现、测试设计和状态核验。阅读者应能仅凭HLD和LLD回答以下问题：

1. 模块负责什么，不负责什么，与哪些模块交互；
2. 每项需求来自哪里，属于规范要求还是OpenHBX设计选择；
3. 请求、数据、状态、token和错误怎样流动；
4. 需要创建或修改哪些文件、类型、接口和算法；
5. 并发、容量、时序、reset和异常条件下应保持哪些不变量；
6. 怎样通过可重复实验判定实现是否完成。
7. 文档、生产代码、测试、配置和验证artifact分别存放在哪里。

### 1.2 参考HFSSS的内容

OpenHBX采用HFSSS HLD/LLD中以下成熟表达方式：

- HLD按“模块概述、需求回顾、系统架构、详细设计、接口、数据结构、流程、性能、错误、测试”展开；
- LLD把HLD下沉为数据结构、头文件、逐函数接口、内部逻辑、状态机、流程图、Debug机制和测试用例；
- 用需求矩阵、组件分解表、结构定义、状态表和流程图减少散文式描述；
- 明确上游、下游、并行依赖、输入、输出和模块边界；
- 对关键资源给出容量、时序、并发和异常处理设计。

参考HFSSS只代表学习文档组织和工程表达，不代表继承其产品需求、实现结论或性能数字。

### 1.3 OpenHBX约束优先级

文档发生冲突时按以下顺序处理：

1. OCP HBF v0.7.0可定位原文；
2. 当前Ramulator 2源码中的实际ABI与生命周期；
3. `TASK1-整体设计方案.md`及跨模块不变量；
4. 模块HLD；
5. 模块LLD；
6. HFSSS、SimpleSSD和其他参考实现。

下位文档不得静默改写上位约束。确需偏离时，必须记录差异、原因、影响和待决策人。

## 2. 客观性与证据要求

### 2.1 内容分类

每个重要结论必须能识别为以下类别之一：

| 类别 | 含义 | 写作要求 |
|---|---|---|
| **规范事实** | OCP HBF明确规定的行为 | 给出章节、表、图或字段定位；不能用常识补齐缺失字段 |
| **源码事实** | 当前Ramulator或参考实现中可定位的行为 | 给出仓库路径和符号；版本敏感时注明revision |
| **OpenHBX设计选择** | 规范未强制、由本项目决定的结构或算法 | 明确理由、替代方案、代价和所有者 |
| **外部依赖** | 依赖UCIe、AMBA、vendor profile或尚未提取的规范内容 | 标记依赖项和解除条件，不臆造默认值 |
| **计划/假设** | 尚未实现或尚待验证的方案 | 使用`PLANNED`、`TBD`或明确假设，不写成现状 |
| **验证事实** | 已由实验支持的结论 | 给出证据等级、日期、CTest入口和artifact位置 |

引用OCP时优先使用“规范要求/允许/禁止”；描述项目方案时使用“OpenHBX选择/约定”。不得用“必须”包装无来源的个人偏好。

### 2.2 可核查写法

- 需求描述必须可测试，避免“高性能”“完善支持”“智能调度”等不可判定表述。
- 性能数字必须附来源、配置、单位、测量窗口或推导公式；vendor参数不能写成OCP保证值。
- 架构图、伪代码和接口签名必须与正文一致，不得出现只在图中存在的组件。
- “当前已实现”必须能定位生产代码；“已验证”还必须满足第11节的证据门槛。
- 未核实的信息写为`TBD`、`SPEC_EXTRACT_REQUIRED`或`EXTERNAL_DEPENDENCY`，并说明关闭条件。
- 不以文档篇幅、文件已创建、代码可编译或fake pipeline通过推断功能完成。

### 2.3 需求来源写法

需求矩阵的“来源”不得只写“OCP”或“代码”。应尽量写成以下形式：

```text
OCP HBF v0.7.0, Section <n>, Table/Figure <n>, <field or rule>
thirdparty/ramulator2/<path>:<symbol> @ <revision>
OpenHBX design choice, ADR-03-002
SPEC_EXTRACT_REQUIRED: <待提取字段>
```

## 3. 文档分层与职责

| 文档 | 回答的问题 | 应包含 | 不应包含 |
|---|---|---|---|
| HLD | 为什么这样分层，模块怎样协作，需要满足什么 | 边界、需求、架构、组件、跨模块接口、主流程、性能/错误策略、验收策略 | 每个私有成员的实现、逐行算法、与代码不一致的大段声明 |
| LLD | 开发者具体怎样实现和测试 | 类型、文件、API契约、状态机、算法、并发、配置、统计、测试接缝、完成定义 | 重新定义HLD边界、复制通用实验流程、引入新的产品需求而不回写HLD |

HLD与LLD必须一一对应并使用相同模块编号。LLD开头必须声明对应HLD、覆盖的需求ID和未覆盖范围。一个系统级概念只能有一个权威owner；其他文档通过完整文件名和章节号引用，不复制一份稍有差异的定义。

## 4. 通用格式

### 4.1 标题、元数据与存储位置

每份HLD/LLD开头至少包含：

```markdown
# OpenHBX <模块名>概要设计

**文档版本**：V1.0
**文档位置**：`docs/HLD_NN_MODULE.md`
**对应文档**：`docs/LLD_NN_MODULE.md`（HLD必填）
**对应HLD**：`docs/HLD_NN_MODULE.md`（LLD必填）
**设计状态**：⚪ `PLANNED`
**适用基线**：OCP HBF v0.7.0；Ramulator 2 `<revision或当前submodule>`
```

所有路径均使用从仓库根开始的完整相对路径，不只写文件名。元数据之后提供修订历史。重大边界、接口或状态机变化提升主版本；内容补充和澄清提升次版本。

每份文档还必须在第1章或LLD逐文件设计前给出存储位置表：

| 内容 | 仓库相对位置 | 说明 |
|---|---|---|
| 本文档 | `docs/HLD_NN_MODULE.md` | 模块概要设计的唯一权威位置 |
| 对应详细设计 | `docs/LLD_NN_MODULE.md` | 与HLD一一对应 |
| 公开头文件 | `include/openhbf/<module>/` | 跨模块允许依赖的边界 |
| 生产实现 | `src/<module>/` | 模块唯一生产实现 |
| 测试 | `tests/<level>/<module>/` | fixture与自动oracle |
| 配置/Schema | `configs/`或模块明确路径 | 仅适用模块填写 |
| 实验artifact | `build/artifacts/<suite>/<experiment-id>/<run-id>/` | 不得写入`docs/`、`src/`或`tests/` |

规划路径表示预期落点，不证明文件已经存在。路径改变时必须同步更新HLD、LLD、`docs/OpenHBF-文件安排.md`和追踪矩阵。

### 4.2 Markdown约定

- 使用ATX标题，章节按阿拉伯数字连续编号；不得出现两个同号章节。
- 代码块必须标注语言；架构、状态和时序图优先使用`text`代码块。
- 表格用于字段、矩阵和对照；段落用于解释原因和约束。
- 符号、类型、函数、路径、状态值和配置项使用反引号。
- 引用文档使用完整文件名和章节号，引用测试使用完整Test/Experiment ID。
- 手工目录不是强制项；若提供，必须与实际标题同步。
- 术语首次出现时给出全称，之后全仓保持一致。

### 4.3 状态图标与颜色语义

状态单元格使用“图标 + 机器可读状态文本”。图标用于快速扫描，反引号中的状态文本才是权威值：

| 图标 | 状态 | 含义 |
|---|---|---|
| ⚪ | `PLANNED` | 只有设计，生产代码尚未完成 |
| 🟡 | `PARTIAL` | 仅部分生产路径完成 |
| 🔵 | `IMPLEMENTED` | 生产代码完成，验证证据不足 |
| 🟢 | `VERIFIED` | 已有符合证据等级的自动验证 |
| 🔴 | `BLOCKED_SPEC` | 缺少决定实现语义的规范原文 |
| 🟣 | `EXTERNAL_DEPENDENCY` | 依赖外部规范、接口或vendor profile |
| ⚫ | `NOT_APPLICABLE` | 经边界分析确认不适用 |

不得单独使用`✅`、颜色或百分比替代状态文本，也不得因文档已创建而升级状态。Markdown渲染器不保证真实字体颜色，因此本规范以彩色圆点的视觉编码为准。

### 4.4 图表规则

图表必须表达正文难以清楚表达的关系，并标出关键owner或边界：

- 架构图：模块、文件组、依赖方向和同步/异步边界；
- 流程图：分支、Busy/Rejected、completion和terminal路径；
- 状态图/表：合法事件、guard、动作和下一状态；
- 时序图：参与者、issue、event、completion、callback和reset竞态；
- 资源图/表：queue、credit、payload、token的取得和释放点。

图中不得只画成功路径。凡是接口可能返回Busy、Rejected、timeout、stale或reset，至少在正文或状态表中给出对应路径。

## 5. HLD标准结构

HLD原则上采用以下十章结构。确实不适用的章节应保留并说明“不适用及原因”，不能用“剩余章节”代替设计。

### 5.1 第1章：模块概述

至少包含：

- **模块定位**：在OpenHBX全局数据流中的位置；
- **职责**：本模块拥有的行为、状态和资源；
- **边界**：明确“包含”和“不包含”；
- **模块关系**：上游、下游、并行模块及依赖方向；
- **关键不变量**：例如Accepted恰好一次terminal、Busy零副作用、completion前不提交未来状态；
- **约束与假设**：规范缺口、产品profile、语言标准、确定性和容量前提。

### 5.2 第2章：需求回顾与追踪

先使用五列进度主表，使范围与状态可以快速扫描：

| 需求ID | 需求描述 | 优先级 | 版本 | 实现状态 |
|---|---|---|---|---|
| `REQ-NN-001` | 一项可独立验收的行为 | P0 | V1.0 | ⚪ `PLANNED` |

进度主表后必须紧跟证据追踪表，不得以可视化为由省略来源和验收：

| 需求ID | 来源/类别 | Owner组件 | Test/Experiment ID | 阻断或验收条件 |
|---|---|---|---|---|
| `REQ-NN-001` | OCP章节、源码符号或OpenHBX设计选择 | `ComponentName` | `TEST-NN-001` | 精确oracle或待关闭缺口 |

要求：

- ID在HLD、LLD、traceability和测试中稳定一致；
- 一行只描述一个可独立验收的行为；
- 需求拆分后保留父子关系，不复用旧ID表达新语义；
- 规范要求和设计选择分别列出；
- 性能需求另列指标、目标、条件、来源和测量方法。

### 5.3 第3章：系统架构设计

至少包含：

1. 模块层次架构图；
2. 请求、数据、control和completion的方向；
3. 组件分解；
4. 状态、queue、payload和时间源的owner；
5. 同步/异步边界和唯一EventQueue关系。

先使用组件总表：

| 组件 | 主要文件 | 职责 | 输入 | 输出 | 拥有状态 | 依赖 |
|---|---|---|---|---|---|---|

总表后为每个生产组件建立独立小节，不能只用一行表格代替设计：

```markdown
#### 3.2.1 `<组件名>`（`include/openhbf/<module>/<file>.h`、`src/<module>/<file>.cpp`）

**职责**：
- 说明该组件唯一负责和明确不负责的行为。

**关键组件**：
- `<TypeOrClass>`：说明类型、状态或算法作用。

**输入与输出**：
- 输入来源、输出目标、token/payload/status方向。

**状态与所有权**：
- owner、生命周期、commit和释放点。

**依赖与边界**：
- 被谁调用、调用谁、禁止的反向依赖。

**对应需求**：`REQ-NN-001`
**实现状态**：⚪ `PLANNED`
```

路径必须具体到计划中的header/source；若一个职责由一组文件共同承担，可以成对列出，但不得只写目录。OpenHBX HBF物理层次固定为`Core Die -> Die -> Bank -> Block -> 4 KiB Page`；Host Channel是ownership维度，NOR不属于TASK1。

### 5.4 第4章：高层详细设计

按组件而不是按抽象口号分节。每个组件至少说明：职责、关键组件、处理规则、状态变化、资源限制、错误/边界和对应需求。HLD可给出关键类型轮廓，但不应替代LLD逐字段和逐函数契约。

有延迟的操作必须明确区分：

```text
admission -> reservation -> issue -> scheduled event -> completion -> commit -> response
```

并说明哪个阶段允许修改权威状态、哪个阶段只持有临时状态。

### 5.5 第5章：接口设计

区分公开接口、内部接口和跨模块异步端口。每个接口至少写明：调用方向、输入、输出、所有权、错误语义、backpressure、时序和线程/事件上下文。接口表模板见第8节。

### 5.6 第6章：数据结构设计

只展示决定架构的核心结构，说明字段组、owner、生命周期、容量和不变量。完整字段定义放入LLD。跨模块值类型必须指出唯一权威定义文件。

### 5.7 第7章：关键流程与状态机

覆盖正常路径和至少以下异常路径：

- admission失败或backpressure；
- 下游Busy/Rejected；
- timeout、failure和retry；
- reset时存在in-flight事件；
- 重复、乱序或stale completion；
- 资源耗尽和最终drain。

### 5.8 第8章：性能与资源设计

至少说明适用项：

- queue/credit/payload容量及达到上限的行为；
- 模拟cycle时序和关键资源EAT；
- 预期并行度、串行化点和复杂度；
- 内存预算公式，而不是只给孤立常数；
- 理论吞吐/延迟上限及限制资源；
- 确定性要求和随机seed来源。

目标值尚无依据时写为可配置项或`TBD`，不得借用HFSSS数字作为OpenHBX结论。

### 5.9 第9章：错误、恢复与可观测性

定义typed error、传播/映射位置、payload是否有效、是否可重试、状态是否提交。说明reset、generation、取消、orphan completion和资源回收策略，并列出关键trace、counter、snapshot和守恒式。

### 5.10 第10章：测试与验收

HLD描述“需要证明什么”，至少给出需求/Test ID、测试层级、production path、核心场景、oracle和证据等级。必须包含以下引用：

> 实验执行、证据保存和状态更新统一遵循
> [`实验与测试执行规范.md`](实验与测试执行规范.md)。

不得在HLD复制Docker、CMake、CTest和通用artifact流程。

## 6. LLD标准结构

LLD应保持HFSSS“可直接指导编码”的粒度，并使用以下结构。章节可按模块特性细分，但信息不得缺失。

### 6.1 第1章：模块概述与约束

声明对应HLD、覆盖的需求、上/下游关系、设计约束、假设和术语。重复HLD内容应摘要并引用，不整段复制。

### 6.2 第2章：需求到实现映射

| 需求ID | HLD章节 | 实现文件/符号 | 状态/算法 | Test/Experiment ID | 当前状态 |
|---|---|---|---|---|---|

每个HLD需求必须在LLD中有实现落点或明确阻断原因；每个生产文件也应至少对应一项需求或公共支撑职责。

### 6.3 第3章：核心类型与数据结构

对每个结构、枚举或强类型说明：

- 定义路径和owner；
- 字段名、类型、单位、合法范围、默认值和含义；
- 构造、有效期、可变性和回收点；
- 线程/事件访问规则；
- 序列化、对齐或ABI要求（若适用）；
- 容量公式和必须保持的不变量。

字段表模板：

| 字段 | 类型/单位 | 合法范围/默认值 | owner与生命周期 | 不变量 |
|---|---|---|---|---|

示例代码只保留影响契约的字段，不伪造尚未决定的完整实现。

### 6.4 第4章：头文件与公开边界

逐个说明公开头文件和内部头文件。公开头文件写明导出的类型/API、允许依赖和ABI责任；内部头文件写明私有协作类型及为何不公开。禁止通过内部头文件绕过模块owner。

### 6.5 第5章：函数与接口详细设计

对公开API、跨模块端口和关键私有函数逐项描述，模板见第8节。简单getter可合并说明；影响所有权、状态、时间或错误传播的函数不得只列签名。

### 6.6 第6章：内部逻辑、状态机与算法

至少覆盖：

- 状态集合、初始态、terminal态和合法转换；
- 事件优先级、同cycle排序和generation检查；
- admission、credit预留、回滚和释放顺序；
- issue/completion/commit分离；
- backpressure、retry、timeout、failure和reset；
- 确定性排序与复杂度；
- 关键算法伪代码及其输入、输出和不变量。

状态转换表使用：

| 当前状态 | 事件/条件 | Guard | 动作/副作用 | 下一状态 | 失败处理 |
|---|---|---|---|---|---|

算法伪代码必须与接口和状态表使用同一术语，不能隐藏错误分支。

### 6.7 第7章：逐文件设计

先给模块目录与存储位置表，再给文件总表，随后逐文件建立独立小节。模板见第9节。目录表至少覆盖本文档、对应HLD、公开头文件根、生产实现根、测试根、配置根（如适用）和artifact根。header/source可以同节说明，但职责、API和实现内容必须分别陈述；测试文件必须说明对象、fixture、输入、oracle和通过条件。

### 6.8 第8章：配置、错误、统计与Debug

- 配置：键名、类型、单位、默认值、范围、验证规则、非法值行为和动态/静态属性；
- 错误：内部错误到公开status的唯一映射、data-valid和retry语义；
- 统计：counter/histogram的owner、递增时点、reset规则和守恒关系；
- Debug：trace点、event字段、snapshot内容、日志级别和失败重放所需信息。

不得使用pointer地址、宿主线程调度顺序或wall-clock作为确定性oracle。

### 6.9 第9章：测试用例设计

LLD描述“怎样证明”，至少覆盖unit、component integration、system、fault/reset和适用的performance/conformance。每项使用第10节模板，并引用[`实验与测试执行规范.md`](实验与测试执行规范.md)。Fake只能位于明确边界，并写清因此能达到的最高证据等级。

### 6.10 第10章：实施顺序、ADR与完成定义

实施顺序按依赖关系列出可独立验证的阶段。对影响边界、算法、持久语义或性能模型的选择记录ADR：

| ADR ID | 决策 | 背景/约束 | 备选方案 | 选择理由 | 代价/后果 | 状态 |
|---|---|---|---|---|---|---|

完成定义必须可检查，例如文件落地、接口接通、状态/守恒满足、指定测试达到指定证据等级和未覆盖项关闭。不能写“功能基本完善”。

## 7. HLD与LLD的粒度边界

| 主题 | HLD写法 | LLD写法 |
|---|---|---|
| 组件 | 职责、边界、关系、主要文件 | 类/结构、成员、函数、依赖、逐文件落点 |
| 接口 | 调用方向和高层契约 | 完整签名、前后置条件、所有权、错误、时序 |
| 数据 | 核心对象及owner | 字段、类型、单位、范围、生命周期、不变量 |
| 流程 | 端到端阶段和关键分支 | 每个event、guard、状态转换、credit动作 |
| 性能 | 目标、瓶颈、预算模型 | 计算式、数据结构复杂度、参数验证、统计方法 |
| 测试 | 验收目标和证据层级 | fixture、输入、oracle、边界、artifact增量 |

若HLD已经包含实现级细节，LLD应引用并补全契约，不复制后再产生两个版本；若LLD发现需要改变模块边界或新增需求，必须先回写HLD。

## 8. 接口详细设计模板

```markdown
#### `<返回类型> function(<参数>)`

**定义位置**：`include/openhbf/<module>/<file>.h`  
**对应需求**：`REQ-...`  
**调用方向**：`Caller -> Callee`

**目的**：一句话说明该接口完成的单一职责。

**参数**：

| 参数 | 方向 | 类型/单位 | 合法范围 | 所有权 |
|---|---|---|---|---|

**返回值**：列出Accepted、Busy、Rejected或typed result的精确语义。

**前置条件**：调用前必须成立的状态、credit和配置条件。

**后置条件与副作用**：分别说明成功、Busy和失败时哪些状态可变。

**时序与并发**：同步/异步、调用上下文、completion方式、同cycle规则。

**错误与边界**：非法输入、重复调用、timeout、reset和stale token行为。

**对应测试**：Test/Experiment ID及关键oracle。
```

所有权必须写清：仅Accepted时是否转移request/payload；Busy/Rejected后由谁保留；completion后由谁释放。不得只写“失败返回错误码”。

## 9. 逐文件设计模板

### 9.1 文件总表

| 路径 | 动作 | owner | 主要职责 | 主要类型/API | 依赖 | 对应需求 | 对应测试 | 状态 |
|---|---|---|---|---|---|---|---|---|

路径必须是仓库根相对完整路径。动作使用`新增`、`修改`、`删除`或`保持`。同一路径只能有一个owner；跨模块调用必须通过公开接口，不能由上层直接修改下层内部状态。状态列使用第4.4节的“图标 + 状态文本”。

### 9.2 生产文件解析

```markdown
#### `<组件名>`（`include/...h`、`src/...cpp`）

**职责**：该文件唯一负责的行为，以及明确不负责的行为。

**头文件设计**：公开/内部类型、API和允许依赖。

**源文件设计**：实现的算法、状态转换、资源和错误映射。

**关键组件**：类、结构、枚举和helper各自作用。

**输入与输出**：数据、事件、token、payload和状态的方向。

**状态与所有权**：持有内容、生命周期、并发访问和释放点。

**错误与边界**：非法输入、容量耗尽、timeout、reset和stale事件。

**依赖关系**：被谁调用、调用谁，以及禁止的反向依赖。

**对应需求与测试**：需求ID、测试路径/Test ID、主要oracle。

**实现状态**：⚪ `PLANNED`（或有证据支持的其他状态）
```

详细程度以“开发者无需再次猜测该文件应放什么”为准。不能只列文件名，也不能用一句话概括整个目录。

### 9.3 测试文件解析

每个测试文件至少写明：

- 测试对象和production path；
- fixture及fake边界；
- 输入、配置、seed和边界组合；
- 自动判定oracle；
- 预期证据等级；
- 通过条件与未覆盖范围。

## 10. 流程与测试用例模板

### 10.1 流程模板

关键读、写、reset、fault或管理操作应同时给出阶段图和分支说明：

```text
receive
  -> validate
  -> reserve credit
  -> Accepted: issue -> event -> completion -> commit -> response
  -> Busy: rollback reservation -> no side effect
  -> Rejected: typed error -> no future event
```

正文必须补充：权威状态提交点、token/payload owner、失败映射、credit释放点和terminal条件。

### 10.2 测试用例模板

| 字段 | 内容 |
|---|---|
| Test/Experiment ID | 稳定唯一ID |
| Requirement | 对应需求ID和设计章节 |
| Objective | 一句话说明证明或证伪的行为 |
| Evidence level | E0至E4 |
| Production path | 经过的真实模块及fake边界 |
| Fixture/Preconditions | revision、配置、能力和初始状态 |
| Input/Workload | 操作序列、地址、payload、seed和边界 |
| Fault/Timing | 故障点、cycle和事件顺序 |
| Oracle | 可自动判定的状态、输出、顺序和守恒式 |
| Budget | 最大cycle、请求数和宿主timeout |
| Artifacts | 本测试特有的成功/失败证据 |
| Pass criteria | 精确通过条件和允许误差 |

至少覆盖正向、边界、backpressure、错误、reset/stale事件和资源耗尽。仅检查“无崩溃”通常不是功能oracle。

## 11. 实现状态与状态更新

所有需求、组件和文件使用以下状态。图标只能补充语义，不能替代状态文本：

| 图标 | 状态 | 含义 | 最低依据 |
|---|---|---|---|
| ⚪ | `PLANNED` | 已设计，生产代码尚未完成 | 文档定义 |
| 🟡 | `PARTIAL` | 仅部分路径或MVP完成 | 可定位部分生产代码和未完成清单 |
| 🔵 | `IMPLEMENTED` | 生产代码已完成，但尚无足够验证证据 | 代码、构建接入和实现核查 |
| 🟢 | `VERIFIED` | 指定范围已由相应自动测试验证 | 满足实验规范的E1-E4证据 |
| 🟣 | `EXTERNAL_DEPENDENCY` | 依赖外部规范、接口或vendor profile | 依赖项和解除条件明确 |
| 🔴 | `BLOCKED_SPEC` | 缺少决定实现语义的规范原文 | `SPEC_EXTRACT_REQUIRED`定位明确 |
| ⚫ | `NOT_APPLICABLE` | 经边界分析确认不属于OpenHBX正式模式 | 书面理由及影响范围 |

状态必须绑定具体范围，禁止用单个“模块已验证”掩盖子路径差异。更新为`VERIFIED`时必须记录运行日期、CTest名称/label、通过数量、构建选项、证据等级、artifact和未覆盖范围。

完整状态门禁以[`实验与测试执行规范.md`](实验与测试执行规范.md)第9节为准。旧build目录、历史日志、手工`g++`、文件存在或agent口头报告不能单独支持状态升级。

## 12. OpenHBX与HFSSS的语义边界

### 12.1 不得直接继承的内容

- HFSSS的PCIe/NVMe不能成为OpenHBX Host协议；OpenHBX使用UCIe/AXI/OCP HBF语义。
- HFSSS的Channel/Chip/Die/Plane层次不能替换OpenHBX的Host Channel ownership和`Core Die -> Die -> Bank -> Block -> 4 KiB Page`。
- SLC/MLC/TLC/QLC、page type、Multi-Plane和Die Interleaving只能作为可选vendor profile，不能写成OCP统一要求。
- NOR、namespace、Trim、传统GC victim、任意page-level L2P和active-data relocation不属于正式OCP HBF主路径，除非上位设计明确引入隔离的兼容模式。
- HFSSS中的实现状态、常数和性能指标不能自动转化为OpenHBX状态或目标。

### 12.2 可以转换借鉴的内容

EAT、command stage、fault injection、BBT、thermal、telemetry、resource budget和测试方法可以借鉴，但必须转换为：

- OpenHBX唯一EventQueue和整数simulation cycle；
- issue与completion分离、completion-time commit；
- 稳定token、generation和reset后stale event隔离；
- Accepted/Busy/Rejected及精确一次terminal语义；
- Host Channel容量切片和唯一物理层次；
- OpenHBX自己的需求ID、typed status和验证证据。

## 13. 写作质量要求

- 先给结论、矩阵或图，再解释原因；一个章节只解决一个问题。
- 使用主动句并明确主语，例如“`BankScheduler`拥有每Bank FIFO”，不写“队列会被维护”。
- 同一概念固定使用一个名称；不要在transaction、request、command之间无定义切换。
- 单位必须显式，cycle、byte、DLU、page、request和host wall-clock不得混用。
- 区分行为要求与示例参数；示例使用“例如”，默认值进入配置表。
- 区分逻辑顺序与实际并发；图中的上下排列不自动代表串行执行。
- 避免大段预期实现代码；关键签名、结构轮廓和伪代码足以表达契约。
- 不在文档末尾追加“覆盖前文”的补丁章节；修改原权威章节并同步交叉引用。
- 文件、类型或路径变化时同步更新需求映射和`OpenHBF-文件安排.md`。

## 15. 实验与测试规范接入

HLD负责定义“需要证明什么”，LLD负责定义“fixture、输入、oracle和测试接缝是什么”，[`实验与测试执行规范.md`](实验与测试执行规范.md)负责定义“怎样执行并留下证据”。

专项设计文档只能补充模块特有的参数、fault point、event窗口和artifact，不得另建与统一规范冲突的构建、Docker、CMake、CTest、证据分级、重放或状态更新流程。正式验证只能依据合规的可复现实验，不得将手工探针或fake pipeline包装为更高级别证据。
